# Third Shot UX simplification audit

Date: August 29, 2026
Scope: mobile UI, information architecture, first-use experience, and end-to-end task completion
Method: current worktree review plus rendered walkthroughs at 390×844 using a seeded local database; selected court flows were also checked against production
Code changes: none

## Executive summary

Third Shot does not have a functionality problem. It has a presentation problem: the interface often exposes all of the app's states, actions, and edge-case explanations at the same time.

The most important change is not a new color system or another visual refresh. It is to make the app answer one question at a time:

> What is the single most useful thing this person can do next, given where they are and what is already happening?

The backend already knows whether someone is away, at a court, arriving, joined, waitlisted, hosting, or finished. The UI should use that knowledge to remove decisions. Today, users are asked to understand the model themselves through terms such as “Available this hour,” “Play now,” “I’m on my way,” “physically ready,” “joined,” “on the way,” and “physical spots.”

The recommended direction is:

1. Keep the four-tab bottom navigation.
2. Make **Play** about one primary job: getting into the next game.
3. Replace three overlapping immediate-play actions with one **Play soon** entry.
4. Show one state-aware primary action per screen.
5. Move settings, management, and competition depth behind clear secondary destinations.
6. Reveal details only when they help the current decision.

## What is already working

These parts should be preserved:

- The four primary destinations—Play, Courts, Community, and Me—are understandable.
- The app uses large mobile targets; all visible controls measured on the Play home screen met the 44px touch-target baseline.
- Join and waitlist backend behavior is fast, and the final waitlist confirmation is clear.
- The current Play card is a good foundation for a state-aware home screen.
- Court selection from the map has a useful compact action preview.
- Modal focus management, keyboard focus styles, retry protection, and server-owned state are unusually thoughtful.
- The functionality supports real social coordination rather than merely listing courts.

The redesign should preserve these strengths while reducing what is shown at once.

## End-to-end journey audit

### 1. Create an account and reach something useful

Current journey:

1. Toggle from Log in to Create account.
2. Create the account.
3. Complete or dismiss **Set your home area**.
4. If an area was selected, complete **Save your courts**.
5. Advance through three generic tour cards.
6. Reach Play.

Pain points:

- Up to five blocking sheets appear after account creation before the user can act.
- The tour explains features generically instead of helping the user complete one valuable task.
- Home-area and tour completion are stored in device-level local storage and marked seen before completion (`public/app-v15.js:16060`). A second account on the same device can inherit the wrong onboarding state.
- City suggestions are clickable generic rows rather than semantic options, and starter-court star buttons are announced only as `☆`.

Recommended journey:

1. Create account.
2. Show one optional setup sheet: **Where do you usually play?** with location or city search.
3. Land directly on Play.
4. Teach saving a court, joining, crews, and rankings when the user first encounters those actions.

Success target: one optional blocking setup screen after account creation.

### 2. Decide how to play soon

Current journey:

- **Available this hour** asks for an intended destination.
- **Play now** asks for the court where the user is physically present.
- **I’m on my way** is discovered only after finding an eligible rally.
- Once checked in, the same intent becomes **Start a rally here**.

Pain points:

- The actions reflect backend states rather than the user's question: “How soon can I play?”
- Their difference is explained only after opening each sheet.
- The same physical arrival task is called **Play here**, **Play now**, **I’m here**, **I’m here & ready**, and **Start a rally here** across surfaces.
- “Start a rally here” may join an existing rally or create one, so the button cannot tell the user what the tap will do.

Recommended journey:

Use one primary action: **Play soon**.

The next sheet asks one plain-language question:

- **I’m at a court now**
- **I can be there in 5–15 minutes**
- **I’m free sometime this hour**

The existing check-in, arrival-hold, and availability functionality can remain unchanged behind these choices.

When the app already knows the outcome, label the action precisely:

- **Join this game** if a rally is available.
- **Start a game here** if no rally exists.
- **Your spot is held until 10:13** after an arrival is confirmed.

### 3. Plan a future game

Current journey:

The sheet shows Where, When, and Who together, plus:

- Right now / Plan ahead
- Eight date choices
- Eight time choices
- Three visibility choices
- Expandable type, player count, level, recurrence, and note fields
- A sticky summary and submit action

Pain points:

- A separate **Play now** route already exists, so **Right now** inside Plan a game duplicates the mental model.
- All questions are visible before the previous answer is needed.
- The crew planner shows disabled visibility choices and roster summaries even though the audience is already fixed.
- Choosing Friends does not indicate when the user has no friends to invite.

Recommended journey:

Use a real three-step planner:

1. **Where?** Show the current/saved court as the default and one Change action.
2. **When?** Show three smart suggestions and **Choose another time**.
3. **Who?** Anyone, Friends, or Specific people.

After each answer, collapse it to a one-line summary. Keep Game options behind **More options**.

For a Crew, skip Who entirely:

> Private to all 4 Saturday Morning Crew members.

The Crew flow becomes **Where → When → Schedule**.

### 4. Join, waitlist, and manage a game

What works:

- Join and waitlist are fast.
- The detail view clearly confirms a waitlist position.

Pain points:

- The item can move to another section immediately after a mutation, while a docked banner appears at the same time. The user's visual anchor jumps.
- Leaving the waitlist requires reopening game details.
- A host's game detail can show attendance, Fill the game, calendar, reschedule, leave, cancel, chat, share, court, and player actions together.
- Leave and Cancel appear as comparable adjacent choices despite having different consequences.

Recommended behavior:

- Confirm changes in place: **Joined ✓ · Undo**, **Waitlisted #2 · Leave**, or **Game started · Cancel**.
- Keep the card in its current position for a short confirmation period.
- Show one role-aware primary action in game detail.
- Put Calendar, Reschedule, Share, Leave, and Cancel under **More**.
- Never present Leave and Cancel as equal adjacent actions.

### 5. Fill an open roster

Current journey:

The sheet always reserves space for Invite friends, Ask the court, and Share anywhere. The current visual is shown in [Fill the game](../marketing/linkedin-launch-2026-08-29/screen-fill-game.png).

Pain points:

- Empty channels and disabled controls remain visible.
- Capacity and invitation guarantees are repeated in multiple paragraphs.
- The sheet can be a second dialog stacked over game details.
- In the tested no-friends state, 89 words supported one useful action.

Recommended behavior:

Adapt the sheet to the best available option:

- Eligible friends exist: lead with **Invite friends**.
- Court chat is available: lead with **Post 1 opening to court chat**.
- Neither is available: lead with **Share game link**.
- Put remaining channels under **More ways to share**.

Use one short roster statement:

> 1 spot left. The first person to join gets it.

### 6. Find and choose a court

Current journey:

The map can show search, location, notifications, four quick filters, current presence, a rally banner, a sheet handle, Map/List, a separate caret, sort, a next-game banner, and bottom navigation before showing a useful court decision.

Pain points:

- The map feels like a control panel rather than an answer.
- **Players here** and **Open games** are two filters for the same likely intent: find activity.
- Tapping a list card inserts a duplicate preview of that same court above the card before the user can open details.
- Quiet cards spend most of their space on `0 here now`, `0 open games`, `—`, and `0 ratings`.
- Search ranks places before courts, so “Los Cab” can show Los Angeles before the exact court Los Cab Sports Village.
- “Open games” counts can include future games that the current viewer cannot actually see or join (`backend/routes/courts.py:275` versus viewer filtering near `backend/routes/courts.py:609`).
- Marker numbers represent court count for one venue and venue count for clusters, despite looking alike.

Recommended structure:

1. Search.
2. One **Active now** filter and one **Filters** button.
3. One or two recommended court cards in the peek state.
4. Map/List switch with one drag handle; remove the separate caret.
5. List cards open details directly; compact preview is only for map-marker taps.

Quiet court card target:

> San Carlo Park
> 0.4 mi · 2 courts · Outdoor · Quiet now

Only show activity badges when they are nonzero.

### 7. Understand and act on a court

Current court detail mixes activity, directions, check-in, playing, scheduling, chat, weather, amenities, home court, edits, conditions, tournaments, website, phone, reviews, and reporting.

The dominant action becomes a large red **Check out** after check-in, while **Play now** remains one of several equal tiles.

Recommended hierarchy:

```text
Los Cab Sports Village                         More
2 at the court · 1 game needs players

[ Find or start a game ]
[ Directions ]  [ Message the court ]

NOW AT THIS COURT
People here
Open games

COURT DETAILS                               View
Indoor · 39 courts · Nets · Restrooms
```

State-aware primary action:

- Away: **Get directions**, secondary **Plan a game**.
- At the court: **Find or start a game**, secondary **Message players**.
- In a game: **Open your game**.
- Check out: low-emphasis action under More or at the page bottom.

Move amenities, hours, reviews, tournament hosting, edit/report tools, website, and phone behind **Court details** or **More at this court**.

### 8. Community, friends, crews, and chat

Current Community flattens DMs, court rooms, clubs, crews, games, leagues, and tournaments into one chronological inbox. Crews have no persistent home; users must find a Crew conversation in Inbox, open it, then tap the header to reach Crew actions (`public/app-v15.js:12436`).

Nearby also combines five skill chips, ready-now rallies, availability states, and up to four actions per player.

Pain points:

- Relationship types with different purposes look like the same kind of inbox row.
- “Build your community” club creation appears even when the user's immediate need is a game or message.
- Crew planning repeats locked decisions, as shown in the [Crew planner](../marketing/linkedin-launch-2026-08-29/screen-crew-planner.png).
- Friends and Nearby expose several row actions rather than one clear next step.
- Tapping a message bubble can secretly react to or delete it; behavior differs between chat types (`public/app-v15.js:13038`, `13235`, and `16479`).

Recommended Community structure:

- **Messages**: DMs and active game chats, with active chats pinned.
- **People**: Friends, requests, and nearby players.
- **Groups**: Crews and clubs, with **Your crews** always visible.

Player rows should show the person, context, and one primary action. Put Challenge, Remove friend, Block, and Report in the profile overflow menu.

Chat should use one visible, accessible message-action pattern everywhere. Normal tapping should not delete or react.

### 9. Me and Settings

Current Me is simultaneously:

- A player profile
- A performance dashboard
- A game dashboard
- A saved-court list
- A settings directory
- An installation guide
- An activity destination
- Feedback and account management

Edit profile adds avatar URL/colors, 21 availability chips, home court, notifications, blocked users, password, and danger-zone actions. Some notification controls save immediately despite appearing below a general Save button.

Recommended structure:

**Me** should contain:

- Player identity and compact stats
- Next game
- Recent games
- Saved courts
- A settings gear in the header

**Settings** should contain separate destinations:

- Edit profile
- Notifications
- Privacy and safety
- Appearance and calendar
- Account

Move Rankings to a clear link from the profile stats or a secondary Competition hub.

### 10. Rankings, leagues, and tournaments

Pain points:

- Compete's empty state provides Create tournament, Start box league, and a floating Create competition action.
- Rankings uses one mutually exclusive control for both geography and time: Near me / Everyone / This month. A user cannot select Near me + This month.
- Tournament and league details are long modal documents containing overview, registration, organizer controls, bracket/boxes, matches, standings, players, chat, calendar, and sharing.
- State/copy mismatches were observed, including Casual selected while explanatory copy began with Ranked.

Recommended structure:

- Use one labeled **Create competition** action.
- Present Tournament and Box league as equal choices.
- Split rankings into two controls: **Near me / Everyone** and **All time / This month**.
- Use full-page competition details with tabs:
  - Overview
  - Matches or Bracket
  - Players or Standings
  - Chat
- Pin only the current user's next required action.

## Copy system

| Current wording | Recommended wording |
|---|---|
| Available this hour | I'm free this hour |
| Play now | Play soon |
| I’m here & ready / Start a rally here / Play here | Find or start a game |
| I’m on my way | I can be there in 5–15 minutes |
| Physically ready | At the court |
| On the way | Arriving |
| Physical spots / spots open | Spots left |
| Plan ahead | Plan a game |
| Fill the game | Find players |
| Ask the court | Post to court chat |
| Ready now | Games starting now |

Copy rule: explain the promise once, in human language. Reliability details such as server windows, retry keys, or whether a signal broadcasts presence should live behind **How this works** unless the user must act on them.

## Delivery sequence

### Phase A — Reduce noise without changing workflows

- Apply the copy system.
- Hide zero activity metrics and unavailable Fill channels.
- Remove duplicate FAB actions and the redundant court-sheet caret.
- Move Check out, destructive actions, and management tools into More.
- Put a gear on Me and move settings into a separate sheet/page.
- Label all icon-only actions.

### Phase B — Simplify the core journeys

- Introduce Play soon.
- Convert Plan a game to a real stepper.
- Reorder court detail around current activity.
- Simplify Courts filters and cards.
- Add stable, in-place Joined/Waitlisted/Started states.

### Phase C — Simplify returning-user depth

- Reorganize Community into Messages / People / Groups.
- Give Crews a persistent home and reduce the Crew planner.
- Standardize chat actions.
- Convert league and tournament documents into tabbed pages.

## Validation plan

The redesign should be tested with these end-to-end tasks:

1. New user creates an account and finds a game that could start soon.
2. User already at a court joins or starts a game.
3. Remote user holds a spot and understands when it expires.
4. Host plans a game and fills one remaining spot.
5. User searches for a court with activity and gets directions.
6. Returning player finds a Crew and schedules the next game.
7. User joins a full game's waitlist, confirms their position, and leaves it.
8. User changes a notification preference without editing their profile.

Suggested usability gates:

- At least 90% of testers correctly choose the immediate-play path without explanation.
- A new user reaches a useful Play screen after at most one optional setup sheet.
- Plan a game can be completed without exposing more than one unanswered question at a time.
- Court search to primary action requires no duplicate selection step.
- Every screen has one visually dominant action.
- Every state mutation leaves an obvious in-place result and management/undo path.
- No normal screen uses “physically ready,” “physical spots,” or server/retry language.

## Bottom line

Third Shot should feel smaller than it is.

The product can keep its full functionality if the UI stops presenting every capability as a peer. Let context choose the next action, let details wait until they are useful, and use one consistent language system across the full journey.
