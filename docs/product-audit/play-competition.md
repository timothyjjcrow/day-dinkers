# Play and competition audit

Read-only product audit of current source on 9 September 2026 UTC. Scope: Play discovery and personal plans, game creation, invitations, rosters, waitlists, attendance, cancellation, repeating sessions, scoring, rankings, tournaments and leagues. Source is the current `public/app-v15.js`, dedicated bracket renderer and backend routes/models. The main auditor performed the browser walkthrough. Unless explicitly identified as browser-observed, findings below are source-confirmed behavior or design recommendations, not newly executed end-to-end test results. No production writes or app edits were made.

Priority: **P1** affects a core task, correctness or trust; **P2** materially improves clarity/usability; **P3** useful after the main workflow is coherent. “Confirmed” means the current code directly establishes the behavior. “Judgment” means a recommendation requiring usability validation.

## Main assessment

The app has substantial depth already: separate discovery and personal plans, roster and waitlist tools, role-aware session actions, score confirmation and reversal, partner consent, connected brackets, and league opponent cards. The next work should make these systems agree with each other. The biggest gaps are durable dates for recurring play; complete personal schedules; clear invitation destinations; honest attendance states; and persistent league scheduling. More explanatory copy alone will not fix these.

## 1. Play home, discovery and live refresh

**Already useful.** Find games and My plans are separate, personal plans ignore discovery filters, local results require a chosen area, time and level filters are applied server-side before pagination, network failures are distinguished from empty results, and related friend sessions are shown. Source: [public/app-v15.js:17414](</Users/timothycrowley/pickleball local /public/app-v15.js:17414>), `:17503`, `:17564`; [backend/routes/games.py:2543](</Users/timothycrowley/pickleball local /backend/routes/games.py:2543>).

**P1 — a refresh interrupts browsing. Confirmed and browser-observed by main auditor.** `startPlayLiveRefresh` clears the cache and renders the whole Play view repeatedly ([public/app-v15.js:37499](</Users/timothycrowley/pickleball local /public/app-v15.js:37499>)). `commitViewRender` replaces all child nodes and preserves only scroll (`:1816`). Open Play now / more-game disclosures and focused controls are not restored. The main auditor opened Play now and watched it collapse during the next refresh without acting. This makes the interface feel unstable even when data is correct. Preserve stable rows and action controls, update changing counts in place, and preserve open disclosures, active focus and scroll. Acceptance: leave Play now or “See all nearby play” open through two refreshes; the menu remains open and keyboard focus stays on the same control.

**P2 — choose play intent before asking implementation choices. Judgment supported by source.** The primary button says Create game, but the common entry is a locked casual six-player session. Ranked creation is inside the separate Play now menu, which also contains at-court, on-my-way and free-this-hour modes (`:17062`, `:17766`). A user planning a ranked game for next weekend should not need to discover it under “now.” Use a single task entry with three clear choices: **Casual session**, **Ranked match**, **Competition**; Then **Now / Schedule** where relevant. Keep the at-court and availability shortcuts on the discovery screen. Each resulting page should display its type consistently in the header, roster, chat, calendar and result.

**P2 — make discovery searchable by actual constraint. Judgment.** Current time chips are Any time, Now, Today and Next 7 days (`:17564`); radius is 10/25/50/100 miles and the level dropdown is numeric (`:17570`). Add a date and time window, court filter, and plain-language level labels (for example “Beginner · 2.0–2.5”). An “open spots only” choice avoids inspecting full sessions when a player needs somewhere to join. A saved alert for a specific filter is a useful later feature, but fix discovery and schedule correctness first. Avoid another large category system.

**P2 — feed completeness. Confirmed structural limitation.** The aggregate feed returns `has_more`/`next_cursor` for up to 100 items, but the Play renderer expands only the loaded array and never loads the next page ([backend/routes/games.py:2543](</Users/timothycrowley/pickleball local /backend/routes/games.py:2543>), `:2668`; [public/app-v15.js:17631](</Users/timothycrowley/pickleball local /public/app-v15.js:17631>)). Add a real Load more or date-paged list with honest counts. This is a scale edge case, not evidence that the current pre-launch list is missing 100 real games.

## 2. My plans and calendar

**P1 — future commitments can disappear from My plans. Confirmed rendering path.** The page counts all `upcoming` items, renders just the first priority item, then calls `playScheduleHtml`, which only renders the next seven days ([public/app-v15.js:17101](</Users/timothycrowley/pickleball local /public/app-v15.js:17101>), `:17507`, `:17530`). Remaining upcoming items are excluded from “more items need attention”; there is no Later section. If two games fall beyond seven days, at most the first appears; if the first priority item is a score review, neither future game appears. Render **Needs attention / Today / This week / Later** with a complete list and one calendar view. Acceptance: games at +1, +8 and +20 days, plus a pending score, are all reachable without another page.

**P1 — personal schedule is not a unified schedule. Confirmed.** The backend contributes only future tournaments whose event start falls in the next seven days; leagues are not included ([backend/routes/games.py:2718](</Users/timothycrowley/pickleball local /backend/routes/games.py:2718>), `:2775`). The client explicitly accepts only `kind === 'tournament'` in addition to ordinary games ([public/app-v15.js:17111](</Users/timothycrowley/pickleball local /public/app-v15.js:17111>)). Individual tournament matches and agreed league matches should appear alongside casual play, with their own court, opponent, time and next action. Keep unarranged league matches in a separate **Arrange a time** section. Calendar downloads and subscription already exist; improve the shared underlying agenda rather than introducing another calendar.

**P2 — numeric level selection is clearer for experienced players than new ones. Judgment.** The matching range correctly says it is a hint, not a gate (`:19059`). Preserve that honesty. ## 4. Invitations and joining

**P1 — Invite by link does not invite into the draft being created. Confirmed.** Planner button `ng-copy-invite-link` calls global `shareInviteLink` ([public/app-v15.js:19863](</Users/timothycrowley/pickleball local /public/app-v15.js:19863>)). That function chooses the earliest existing public scheduled game from active/cached games, otherwise creates a general player-invite URL (`:4169`). It can therefore share an unrelated existing game while the user is composing a new one. Change the planner action to **Create session & get invite link** only after a real session exists, or label a pre-creation action explicitly as **Invite a friend to Third Shot**. The URL and preview must show the same session the user is viewing.

**P1 — a new user cannot straightforwardly create a private game for existing offline friends. Confirmed limitation.** Invite only is disabled without existing invite candidates, and submission requires at least one selected existing player ([public/app-v15.js:19008](</Users/timothycrowley/pickleball local /public/app-v15.js:19008>), `:20389`). This demands building an in-app social graph before arranging a simple private game. Add revocable, unlisted session invitation links, with host approval or explicit link access rules; preserve the currently strong private-roster safeguards. Account creation should complete the selected RSVP, not force the user back through Community.

**P2 — joined state should summarize the commitment. Judgment.** The existing “You’re in” and Undo are good (`:35170`). Immediately show **Date/time, court/meeting point, free/cost, who is hosting** and useful **Add to calendar** / directions actions. Add no automatic permission prompt before this success state. Public preview and authentication-gate observations are in the main audit, rather than repeated here.

## 6. Waitlist, arrival and host changes

**P1 — waitlist promotion can falsely imply a confirmed commitment. Confirmed.** `_promote_from_waitlist` immediately adds a roster row with `attending_at=utcnow()` and sends “you’re in” ([backend/routes/games.py:6153](</Users/timothycrowley/pickleball local /backend/routes/games.py:6153>)). A player who joined a waitlist days ago may no longer be available. Offer a time-limited spot with **Accept / Pass**, particularly near start time; preserve optional automatic acceptance only when the player explicitly chooses it. The roster should show Offered until accepted and advance the queue when the offer expires.

**P2 — host handoff lacks the new host’s consent. Confirmed behavior, design improvement.** The old host can choose a replacement; backend otherwise selects the first remaining player and immediately gives them hosting plus a standing RSVP for recurring sessions ([backend/routes/games.py:6389](</Users/timothycrowley/pickleball local /backend/routes/games.py:6389>)). Replace implicit takeover with **Request handoff** and explicit acceptance, plus a clear fallback if nobody accepts. Existing transfer and cancellation confirmations should be reused; this is not a request to remove those tools.

**P2 — immediate-play concepts need visual continuity. Judgment.** Availability for an hour, ETA holds, physical check-in and session membership are distinct. Current protections against stale presence/duplicate rallies are substantial. Present them as a small progression **Available → On my way → Here → Playing** with the current court, expiry/ETA and one change/cancel control. Do not imply that “Free this hour” guarantees an available court or another person’s presence. No GPS permission or distance enforcement was tested by this source audit.

## 7. Weekly sessions and completed play

**P1 — recurring sessions need separate dates as durable records. Confirmed architectural gap.** `roll_forward_recurring` moves the same Game row’s `scheduled_at` to the next date ([backend/routes/games.py:2252](</Users/timothycrowley/pickleball local /backend/routes/games.py:2252>), `:2287`), updates its roster, and does not create a completed occurrence. Completion and scoring explicitly reject recurring games (`:7332`, `:7198`). Thus the app cannot reliably show the actual attendance/results for each past weekly date, and an old shared game link changes meaning as the row advances. Use **Series → Occurrences**, with a stable series overview plus a distinct URL, roster, attendance and chat context for each date. Add an upcoming-date strip and an explicit **This date / Future dates** editing scope.

**P1 — current recurring completion controls can promise an unsupported action. Confirmed code-path mismatch, not exercised in browser.** For a scheduled group session that has started, the renderer offers **Wrap up session** based on group size and roster count ([public/app-v15.js:35010](</Users/timothycrowley/pickleball local /public/app-v15.js:35010>)), even though the API rejects weekly recurrence. A weekly two/four-player game can similarly get a score-entry branch. Render capabilities returned by the server consistently; then implement per-occurrence wrap-up rather than merely hiding it.

**P1 — recurrence rollover ignores session duration. Confirmed.** Due rows are selected three hours after start ([backend/routes/games.py:2254](</Users/timothycrowley/pickleball local /backend/routes/games.py:2254>)), despite the planner allowing longer durations. A six-hour weekly event can advance while it is still in progress. Occurrence completion/expiry must use its explicit end time (with a documented fallback when none exists).

**P2 — actual attendance should not overwrite all participation history. Confirmed behavior; feature recommendation.** Casual wrap-up accepts an attendee subset but removes non-attendees from the roster ([backend/routes/games.py:7359](</Users/timothycrowley/pickleball local /backend/routes/games.py:7359>)). Preserve RSVP, cancellation and actual attendance separately, and let players correct a mistaken attendance report. A friendly “We played” check should not silently erase another person’s prior RSVP. Existing casual no-score completion and Play again are good foundations.

- **Competition first viewport (P2):** In 390px-wide screenshots, the first opponent/matchup begins roughly 450px down the league view and 600px down the tournament view. These are visual estimates from the populated demo, not instrumented or universal measurements. Compact the header and duplicated explanations, keep a concise sticky round selector, and make the next matchup visible sooner. Preserve full context in expandable details.
- **Agenda scope (P1):** The current personal feed joins `GamePlayer` only ([backend/routes/games.py:2389](</Users/timothycrowley/pickleball local /backend/routes/games.py:2389>)), so unaccepted invitations and waitlist entries are not part of that returned schedule even though the frontend has labels for those states. They may remain accessible through notifications or a game link; the gap is that My plans is not yet an authoritative list of all commitments and pending decisions.

## Recommended build order for these areas

1. Fix Play refresh interruption, complete My plans, wrong invitation destinations and ranking eligibility/pagination messages.
2. Introduce durable recurring dates with usable completion and date-scoped RSVP/history; make every session action respect backend capabilities.
3. Unify scheduling across sessions and competition matches; add actual league time proposals/acceptance.
4. Separate invitation, attendance confirmation, offered spot and physical arrival; add consented waitlist/host handoff.
5. Refine the visible hierarchy: one task entry, clear session type, cost/access above Join, personal next match before full competition detail.
6. Add court-based tournament operations, schedule warnings/delay handling and round-specific league standings after the rules are decided.

## Verification limits and useful test scenarios

The audited code already includes extensive targeted tests (for example `tests/test_game_recurrence_patterns.py`, `test_game_attendance_frontend.py`, `test_competition_detail_completion.py`, `test_tournament_partner_consent.py`, `test_ranked_streak_rollback.py`). These existing tests were inspected selectively, not rerun as proof of new findings. Some primarily assert markup/source patterns and cannot establish novice comprehension. No score, invitation, RSVP or competition mutation was sent during this audit.

Prioritize executable scenarios for each concrete gap: an expanded Play menu through polling; future games beyond seven days; viewer rank outside the first page; new account planning private play with non-members; a six-hour recurring session; a past recurring date whose link stays stable; waitlist offer acceptance after a long delay; one of two partners arriving; overlapping tournament times; a league time accepted then rescheduled; and disagreement resolved without duplicating a match.
